## Demonstrated defect: feet-relative coordinates submitted as absolute world coordinates

`native_body.cpp:584–615` resolves animated hand targets in the model/head frame. At `679–693` the body job publishes grip position as `toWorld.rotate(hand.grip)` and orientation as `toWorld * hand.orientation`. This rotates the position offset into world axes but deliberately does NOT add actor translation. Existing logs explicitly call these feet-relative world axes; this repair also documents that contract on the public `OverlayTracking` fields. Actor translation exists separately (`probe.root`, transform[12..14]).

The original visible-glove fix, commit `96aed2abb432588eb5f031405aa06833af0c7c6a`, passed that feet-relative grip directly to `mapAimToDisplayedGrip` at `game_xr.cpp:2995–3005`. Its helper merely called `webShooter(mappedGrip, hand)`. It replaced a previously absolute `Input::Hand::aim.position` with a relative position. `game_swing.hpp:841–861` copies this into `Input` unchanged; there is no downstream addition of player feet.

`game_swing.cpp:540–557` only adjusts orientation for forearm/web angle. `game_shooter.cpp:1167–1207` passes this pose into `Shooter::aim`; `shooter.cpp:42–93` uses it for muzzle position, target selection and raycasting in absolute game world space. Queue dispatch `game_shooter.cpp:514–520` adds only movement SINCE sampling (current feet minus sampled feet), not the missing full feet translation. Both gadget and fallback fire paths use this already-wrong origin in `muzzleMatrix` at `505` and `578`. So weapon emitters/physics, target queries and markers can all agree with each other while being in the wrong place in the game world.

This is independently demonstrable, not inferred from object pointers: the production legacy helper, given feet(-140,35,820), has an832.601m muzzle error. The repaired helper reports0.000m for the same input. The exact before/after standalone repro sources/binaries live outside the repo at `/workspace/spidyvr-playtests/2026-11-08-0828/analysis/origin-{red,green}.cpp` (red intentionally exits1, green exits0).

The latest compatibility log has matching evidence: mod-b lines4801/4803 publish grip offsets around(0,1,-0.5), explicitly feet-relative; line4806 gives displayed combat head around(162,3.56,973.58) in world space. Lines4793–4876 count9 animation fires while these offsets/valid arm solves are present. Actual dispatch vectors were not logged in that older compatibility build, so the exact gameplay outcome of each shot remains unknown.

## Minimal patch

`mapAimToDisplayedGrip` now REQUIRES a feet anchor and adds it exactly once before constructing the wrist shooter. Orientations are already world-space and receive no extra actor yaw. The sole production caller supplies `motion.anchor`, the same current player-feet anchor used for the tracking frame. Invalid feet reject without mutating the original aim. Existing hand-tracking/overlay/grip-out gates remain unchanged. Thus while animation owns and a free hand maps, both `input.hands[i].aim` (swing/engine) and `motion.swing.hands[i].aim` (saved marker pose) get the same absolute muzzle. The working SpidyVR branch never enters this mapping and is unchanged.

## Serial/thread/transition audit

XR sampling publishes `pose` and `handView` atomically under native_body commandLock late in the loop (`game_xr.cpp:6736–6789`; native_body:1013–1018). A body pose job resolves that command and publishes OverlayTracking with its command serial and local job counter. XR reads the last completed sample under solveLock early in the next loop (game_xr:2997; native_body:1003–1007). Expected delay exists; the current mapping only gates targetFrame/valid/tracked, not owner-generation or a wall-clock pose lease. Forearm data is sampled separately and has a separate job/age gate. These sample streams can straddle ownership edges; they are NOT an atomic action-frame snapshot.

Pending shooter records hold ShotRequest/player record/sample feet/queued time (`game_shooter.cpp:364–369`) but no owner generation or body serial. `fireQueued` expires by time then dispatches without ownership-generation validation (`867–882`). `fireNow` translates muzzle by player travel while keeping the sampled absolute aim point fixed (`514–520`); this could affect near targets during fast movement in either owner. Those are verified architectural gaps/candidates, not demonstrated causes of the owner-specific report. They are deliberately not changed speculatively in this minimal repair. Do not suppress legitimate queued shots or add grip cancel until the transition action contract is agreed.

### Dispatch lock/concurrency review

Known lock graph: start uses lifecycle -> updating (released) -> dispatch(exclusive) -> queue; enqueue uses updating(shared) -> queue, releases queue before output; dispatch copies queue and RELEASES queue before dispatch(shared) -> engine/flying/collision locks; revocation releases Swing control BEFORE waiting for dispatch(exclusive) -> queue, then releases both before output. No inspected output/flying/webbing path reacquires dispatch/control in reverse order. Native callbacks beyond this source are not proven deadlock-free; the engine call runs under a shared lease and cancellation may wait for it. An already admitted engine call may finish; after revocation returns, copied old batches and late old-input enqueues cannot begin dispatch. Raw physical grip time is not a retroactive projectile-removal boundary.

Factored dispatchAction/revokeActions into the actual runtime algorithm with RAII lease release; native adapter uses SRW, portable tests use std::shared_mutex, Windows tests select SRW. Validation is under the lease immediately around actual fireNow, not only enqueue; expiry rechecked there too. Tests cover active-call revocation waiting, copied old generation, old serial with new generation, independent gadget epoch, new work acceptance, callback exception cleanup and stress.100 repeated runs passed:1,200,000 dispatch attempts /25,000 revocations. This is functional concurrency testing, not ThreadSanitizer or real native callback execution.
